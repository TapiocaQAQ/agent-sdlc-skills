# External AI Review(外部 AI 第二審)

給一份**已完成、可以開 PR** 的變更找第二雙眼睛,然後把它真正找到的問題修掉。
**reviewer 是一個介面,不是寫死的模型**——換 reviewer 是實作這個介面,不是重寫這條流程。

## 何時用

- `/agent-sdlc:pr-prepare` 產出 PR 描述之後、commit 之前,想要一次獨立的第二審時。
- 對映 appleboy 的 `/loop 3m /copilot-review`:配 `/loop` 反覆重審直到收斂。

## reviewer 介面(可插拔)

一個 reviewer 必須能:① 收下「變更摘要 + diff + 重點提示」,② 回一份發現清單(`file:line` + 建議修法)。

- **v1 實作 = sub-gemini**(Gemini Pro,經你已登入的 Chrome 驅動,細節歸 `sub-gemini` skill 管)。
- 之後有 Copilot / Codex CLI 或任何其他 reviewer,照同一個介面實作就能接上——本流程不變。

## 流程(單輪 check-fix)

每次調用跑**一輪**。配 `/loop` 重複到收斂。

### 1. 備審查輸入

- 用 `git diff`(分支用 `git diff main...HEAD`)取變更。
- 摘要:改了什麼、`classify-change` 的 leaf/core 裁決、以及要 reviewer 最用力看哪裡(金額精度、認證、邊界、錯誤路徑等)。
- ⛔ **敏感資料紅線——這是讓「外部」reviewer 得以安全存在的那道閘。** 任何東西離開本機之前,
  **剝除每一份真實資料、密鑰、個資**:真實 CSV/DB 內容、載具號碼、驗證碼、`.env` 值、API key、token、真實使用者紀錄。
  只送**原始碼 diff 與合成範例**。`copilot-review` / `codex-review` 不需要這道閘——它們的 diff 本來就在 GitHub 裡;
  這裡 diff 是**送出去**的,所以去敏是強制的。某個 hunk 不脫敏就沒法給看,就換成合成佔位符,或整段略過並註明。

- ⛔ **講清楚 payload 的邊界,而且要送「算出來的成品」,不是只送產生它的規則。**
  reviewer 分不出「這個檔案缺席是因為不在範圍內」和「這個引用是死連結」,
  也無法在只拿到**改寫表**的情況下判斷改寫後的文字讀起來對不對。
  2026-08-07 實測一輪:**7 條被駁回的發現裡有 3 條是輸入造成的,不是 reviewer 的錯**——
  兩條說某段描述失去了進入條件(倖存的文字在前兩句就寫了,但那兩句不在 payload 裡),
  一條把還活著的交叉引用報成死連結(兩個檔都在版控裡,只是不在 diff 裡)。
  - 所以:把「有被引用、但刻意排除」的檔案列出來,並說明它們存在。說清楚哪些產物是生成的。
  - 變更若是一種**轉換**(改寫表、codegen 規則、migration),就附上受影響項目**實際輸出的前後對照**。
    那一輪的實測成本:+29,230 字元、該 lane +41%、整輪 +10%——比起它消掉的那些駁回,很便宜。
    **這是「瞄準」的改動,不是截斷**:沒有任何東西被拿掉。

### 2. 委派 reviewer(v1: sub-gemini)

- 調用 `sub-gemini` skill 並照它的完整劇本走(開全新 `/app` 分頁、先 fill 再用 JS `eval` 送出、
  用 `get url` 驗證真的送出、輪詢到「停止回覆」控制項消失、再讀最後一個 `message-content`)。
  瀏覽器細節歸 `sub-gemini` 管,不在這裡複製一份。
- prompt 要自包含:變更摘要 + **去敏後的** diff + 明確要求:
  「以 `file:line` 列出每條發現、**你會怎麼用我給你的材料去證偽這條主張**、以及怎麼修。」
- ⛔ **要的是「證偽方法」,不是「嚴重度」。** 嚴重度是 reviewer 給自己的作業打分,而且它打得很寬鬆:
  實測跨一次 code review 的兩輪 fan-out,**13 條被標成 `blocker`;其中 9 條在檢查後被駁回或降級,
  真正影響到執行期行為的恰好只有 1 條**。有一個 lens 交了 5 條 blocker、**0 條倖存**。
  嚴重度欄位灌水零成本,而且它告訴你的東西,你在第 3 步本來就會知道。
  - **證偽方法**買到的是什麼:發現送達時**自帶實驗**。把那一輪重播一次,每一條被駁回的 blocker
    都是被**我自己設計的一次量測**殺掉的(schema 有沒有任何 key 含被封鎖的名字?`$ref` 到底出現在哪?
    anyio 實際上往那個 group 裡放了什麼?)。要求它先交食譜,等於把這份工作移給 reviewer,而且一條發現都沒少。
  - 你想留嚴重度可以留,但**把它讀成 reviewer 的信心,永遠不要當成你的**——更不要讓它決定你的工作順序。
  - ⚠️ 它自己的失效模式:reviewer 可以用編造嚴重度的同一種方式編造一個聽起來很合理的證偽方法。
    量測仍然由你選、由你跑;食譜是提示,不是結果。
  - ⛔ **跑完證偽方法,還要回頭查它預設成立的那個前提。** 證偽方法測的是**主張**,測不到**主張所援引的需求**。
    2026-08-07 實測:一條發現說某支探針的 `samples_ms` 必須排序「才能滿足跨執行比較的需求」,
    附的證偽方法跑起來乾乾淨淨——那個陣列的確沒排序。但這條發現仍然是錯的,因為**根本沒有那個需求**:
    沒有任何東西會跨執行比較那個陣列,而排序會毀掉它唯一攜帶的「單次執行內漂移」訊號。
    對每一條發現問:*它假設了什麼是必要的,那真的必要嗎?*
  - ✅ 這個欄位真正付錢的地方:那一輪有兩條發現是被**同一次**量測殺掉的,
    而讀它們的證偽方法才讓我知道該跑哪一次量測。它們自己的食譜都沒用
    (其中一條 grep 的是 reviewer 自己發明的變數名),但它們暴露了**共用的那個假設**——
    於是我去證偽那個假設,而不是去證偽那兩條主張。
    **食譜的價值常常是它暴露的假設,不是它指名的那個檢查。**

### 3. 驗證 reviewer 的回覆(Claude 的責任——**不要盲信**)

- Gemini 的幻覺率比 code-tuned 機器人高,所以**每一條發現都是待查證的主張,不是待執行的指令。**
  逐條對真實 diff 確認:那段碼與那個 `file:line` 真的存在,而且問題是真的,才收。
- 任何牽涉事實、版本、API 契約的發現,**獨立查證**,不要採信 Gemini 的說法。
- 幻覺的、過期的、與架構衝突的一律駁回,並**記下每一條被駁回的理由**
  (這是 appleboy 那句「resolve 之前先回一段理由」的本地等價物)。
- ⛔ **一條發現指的是一條軸,不是一份清單。收掉它之前,自己把那條軸雙向掃完。**
  reviewer 是抽樣,不是枚舉。只驗證它剛好看到的那一個實例然後收工,等於把樣本當成母體。
  2026-08-09 PR-A 實測:那條發現原文只是**「文件的覆蓋宣稱漏講了 `input_schema`」**——
  表面上就是一句話寫太滿。沿著那條軸掃(下游閘門**實際上**掃什麼?它的檢查我們**全部**跑過了嗎?)
  才發現整份稽核從頭到尾**只跑過那個閘門兩個散文檢查中的一個**;
  補跑另一個多抓到兩支工具,並把一個承載安全性的下限從 5 提到 7。
  **那條不在 reviewer 的回覆裡**,照第 3 步的字面走(確認 `file:line`、改掉那句話)就會直接漏掉。
  → 對每一條收下的發現問:*這個錯誤的一般形式是什麼,它還可能在哪裡?* 枚舉那個集合,不要靠模式比對找第二個實例。
- ⛔ **觀察與藥方要分開評價——它們會各自出錯。**
  一條發現可以**對缺陷的判斷正確**、**對修法的建議錯誤**,整條照收就會把錯的藥方 ship 出去。
  2026-08-07 同一次 review 實測到兩次:
  - reviewer 正確找到某個掃描漏了一種拼法,建議把空白正規化。它自己的量測看起來免費——
    **35 筆已記錄輸入上 0 個 false positive**。但那個掃描失敗會擋**啟動**,而拿合理的英文去打,
    它 6 打 6 全中:"Returns host health and uptime"、"A cluster health summary is not available here"
    ——後面那句正是這個專案自己會寫的句子。照它改會 ship 出一個開不起來的容器。
  - 另一條正確找到一個沒有防護的引用,建議把一張不相干的表拿來兼差存它,那會破壞那張表自己的不變量。
  兩次的正解都是**收下觀察、重新設計藥方**——而且邊界如果是刻意的,
  就**把那個界限寫下來並用測試釘住**,免得下一輪又重新提出危險的那個版本。
  ⚠️ 拿**你手上有的資料**去量測藥方是不夠的,如果那個藥方防的是你**還沒拿到**的資料;
  要拿「合理會到來的東西」去測。

### 4. 修正

- 逐條修掉收下的 `blocker` / `warn`,能釘的地方補一個測試把修正釘住。
- `nit` 自行斟酌。
- ⛔ **掃整條軸,不要只補那個實例——這是機械動作,不是提醒。**
  reviewer 報的是一個**樣本**;同一個錯誤幾乎一定以別的措辭存在於別處。
  **每修完一條,立刻 `grep` 整個檔案/模組裡你剛動過的每一個詞**(錯的宣稱、改正後的宣稱、數字、識別字),
  逐個命中檢查——**在進到下一條發現之前**。而且**雙向掃**:你把一個錯的 ✅ 降級了,
  也要回頭找那個本來應該是 ✅ 的 ⚠️。
  - ⛔ **它必須產出一張表,否則它不會發生。** 寫成提醒就會被跳過——實測:2026-08-07 的一次 code review,
    這條規則整段時間都在這支 skill 裡,而**連續三輪逃掉的缺陷全都是上一輪自己那個修正的兄弟位置**
    (宣稱「三個分支全涵蓋」但只涵蓋兩個;三個一模一樣的 matcher 有兩個做了 case-fold、第三個沒動;
    一個寫下當時就已經錯了的計數)。所以把它變成產物,在下一輪開始前落進 mem-tmp:

    | 我改過的詞 | grep 命中 | 逐個命中的判定 |
    | --- | --- | --- |

    「詞」是你動過的每一個識別字、數字、片語——**外加改正後的形式**,這樣才是雙向掃。
    第一次產出這張表的那一輪找到 **7 個位置,其中 6 個 reviewer 完全沒提過**。
  - ⛔ **任何「X,因為\<某段算術\>」形式的宣稱都要自己一列,而且判定欄必須秀出重算過程,不是 yes/no。**
    計數你可以 grep,公式你必須**求值**;而一段寫得很有自信的公式,讀起來和一段驗算過的一模一樣。
    2026-08-07 實測:某支探針的 docstring 說把樣本數從 5 提到 10 就能讓 nearest-rank p95 不再等於最大值。
    `ceil(0.95 × 10) = 10`——10 個裡的第 10 個,**還是最大值**。
    **記錄下來的資料本身就是它的反證**(每一列 p95 == max),而這條宣稱撐過了**五輪**審查
    和一次 max-effort code review,因為每一輪都把它當成量測結果來讀,而不是拿去求值。
    掃那一條又找到了第二個 reviewer 從沒提過的位置。要納入的:百分位/索引算術、「N of M」、
    百分比、門檻值、複雜度宣稱,以及任何把兩個數字連起來的「所以就是說」。
  - 最便宜的執行時機是**趁 reviewer 還在生成的時候**——你本來就知道自己上一輪改了什麼。
  - ⚠️ 一張全零命中的表要讀成**「我瞄錯方向了」**,不是「這段碼很乾淨」。
    而且它只抓得到**grep 得到的**兄弟:同一個假宣稱換句話說,它是看不見的。這是方法的界限,不是跳過它的理由。
  - 這條是承重的證據:2026-08-06 的一次文件審查,**連續四輪**的頭號 blocker 都是漏掃了**上一輪**的修正
    ——一個錯的定義就這樣安靜地傳播到第三個位置。開始跑機械 grep 的那一輪,7 條發現裡有 2 條是我搶在
    reviewer 之前抓到的,其中一條 reviewer 從頭到尾沒找到。
  - 一條發現如果**沒有可掃的詞**,那是「這條主張太模糊」的訊號——先把它重述成可檢查的東西。
- 修正累積在工作區——**沒有逐輪 commit/push**(還沒有 PR 可以推)。
  收斂之後用 `/agent-sdlc:commit-message` 一次 commit;PR 用 `/agent-sdlc:pr-prepare` 交棒。

### 5. 為這一輪計分,然後配 /loop 收斂

- 用 `/loop` 重跑本 skill,直到 reviewer 對當前 diff 回**沒有新的 `blocker` / `warn`**。完全乾淨的一輪是理想的停點。
  - 實務上非決定性的 reviewer 很少給你這種一輪,所以可運作的停止條件是
    **連續兩輪 native accepted 為 0**——照下面的計分卡計。
- 每一輪把**修了什麼**與**跳過什麼(附理由)**記進 mem-tmp——這是稽核軌跡
  (appleboy 記在 GitHub PR thread,我們記在 mem-tmp)。

#### ⛔ 每一輪都要以一張計分卡收尾——這不是可選項

> 🧪 **暫行——整個小節是一個實驗。** 2026-08-06 依使用者要求採用,目的是讓
> 「這個 loop 到底值不值它的成本」變成可回答的,而不是一種感覺。
> **它會留到使用者說這個問題已經有答案為止,然後才拆掉。**
> 不要讓實驗僵化成永久儀式:如果你在填這張表而它沒有改變任何決定,直說,並提議移除。

沒有數字,你就分不出「reviewer 還在找我漏掉的東西」和「reviewer 開始在編修我的散文」,
於是 loop 退化成**加輪數**而不是**修管線**。不用人問就主動報。
它是**artifact-agnostic** 的——同一張表適用於程式碼、文件、設定檔、設計審查。

| 指標 | 怎麼算 | 為什麼在這裡 |
| --- | --- | --- |
| 成本 — payload | 字元(或 token)× lane 數 | 原始量 |
| 成本 — wall clock | 每個 lane 的收割秒數 | 原始量 |
| 發現 / 收下 / 駁回 | 逐條判定 | 命中品質 |
| **Native accepted** | 收下**且不是你前一輪自己寫的文字**——註明那段文字的來源 | 分開「找到我漏掉的」與「共同編輯我的草稿」 |
| 🔴 **逃掉的缺陷** | **後面**某一輪或人審抓到、但前面某一輪本來就該抓到的有效發現 | **這才是效能指標**——回溯計分,不是自評 |
| 可機械化比例 | 有多少收下的發現,一個決定性檢查本來就做得出來 | 告訴你該把什麼搬出抽樣器 |
| 我自己順手掃出的實例 | 每條發現額外找到幾個位置 | 量抽樣缺口 |

##### ⛔ 數字要並排報,永遠不要壓成單一分數

- **不要指定主指標,也不要把成本除以發現數。** 單一比值就是那個會被拿去優化、取代工作本身的東西。
  目標是 `(成本, 逃掉的缺陷)` 這一對:**讓更少缺陷逃掉、而且更便宜**——*不是*「每 token 找到最多發現」。
- ⛔ **知道自己會怎麼作弊,否則你會不小心作弊。** 這一節的舊版本把「成本 ÷ native accepted」當主指標。
  那個數字兩端都可以鑽,而且失效模式是具體的:
  - **分類漂移**——把一條邊界發現叫做 native,分數就變好。
    *緩解:`native` 要有證據——指名是哪一輪、哪一顆 commit 引入了那段文字。*
  - **拆分**——把一個缺陷報成三條發現,計數就變三倍。
  - **縮小 payload**——送得少、成本降,覆蓋率跟著安靜地降。
  - 🔴 **提早停**——一個 cost-per-find 指標會**獎勵你在發現開始變貴的當下退出**,
    而**又貴又晚的那些發現才是有價值的**。2026-08-06 實測:全 run 最貴的那一輪產出了該 run 最大的一條修正。
    *一個會叫你在它之前停下來的效率指標,是壞掉的指標。*
- **只看採納率會騙人。** 一輪可以每條都收下卻毫無價值,如果全部都是關於你上一輪的措辭。
  要看**兩輪**,不是一輪(見「讀 N 份結果」)。
- **計完分,為下一輪指名一個具體改動**——換一個 lens、把某個檢查搬進腳本、把注意力對準某個區域。
  不是反省,是下次真的會不一樣的東西。⛔ **然後在說出口之前,先讓它過下面那四道檢驗。**
  「payload 小一點」**不是**一個可以單獨提出的改動——它只能作為「把某條軸機械化」(檢驗③)的**後果**出現,
  永遠不能當目標。
- **把學到的東西回寫進這支 skill。** 計分卡的存在是為了改管線,不是為了裝飾 log。

#### ⛔ 帶一份跨輪的覆蓋帳本——沒被檢視過的區域不等於乾淨的區域

計分卡告訴你的是 *reviewer* 還有沒有生產力。它告訴不了你 artifact 的哪些部分**從來沒被看過**
——而那正是最老的缺陷所在,因為它們在第 1 輪之前就寫下了,之後沒有任何一個 lens 指向過它們。

⚠️ **第 4 步的掃描在結構上蓋不到這件事。** 那個掃描錨定在**你剛改過的詞**上,
所以寫過一次、之後沒再編輯的文字**永久落在它之外**。兩個機制是互補的:
掃描找的是**這一輪**編輯的兄弟,帳本找的是**沒有任何一輪**質疑過的區域。
2026-08-07 在一次 5 輪的 code review 上實測:第 1–3 輪的 9 個 lens **全部**只問了正在被編輯的那三個模組。
build 檔與量測探針到第 4 輪才第一次被檢視,而該 run 最老的那個缺陷——一條在 gate 4 寫下的百分位宣稱,
求值即錯,撐過五輪審查**和**一次 max-effort code review——直到第 5 輪才浮出來。

帶一張表跨輪往前走,並讓它決定下一輪 lens 的順序:

| 區域 | 輪次 · lens | 那個 lens 問了什麼問題 |
| --- | --- | --- |

- **沒有任何一列的區域,下一輪就給它一個 lens**,順位排在「再掃一次熱門模組」前面。
  這是純加法,改的是**瞄準**,不是 payload(見「瞄準不是截斷」)。
- ⛔ **「問了什麼問題」那一欄才是承重的——只有檔案清單的表比沒有表更糟。**
  沒有問題的覆蓋只記錄了*有人看過*,而後面的輪次會把它讀成*這裡是乾淨的*。
  同一個 run 實測:第 4 輪的 build lens **確實**讀了那支藏著百分位缺陷的探針,
  而且針對那個檔回了一條發現,但那條被當成「發明出來的需求」駁回了。
  一張只有檔案的帳本會把那支探針標成*已覆蓋、無發現*並降低它的優先序。
  那個缺陷之所以浮出來,是因為第 5 輪對那個區域問了一個**不同的**問題,不是因為它被多看了一眼。
- ⚠️ 它自己的失效模式:帳本只記錄得下你想得到要問的問題,所以一條沒有人想過的軸,
  讀起來會和一個覆蓋良好的區域一模一樣。它界定的是**重複**,不是**盲區**。
  一張填滿的表意思是「別再重複問了」,永遠不是「所有東西都檢查過了」。

#### ⛔ 每一個提案改動都要先過這四道檢驗——**在你說出口之前**

一個管線改動是一則對未來的主張。自己跑這四道;不要讓使用者去找那個洞。
四道都是 artifact-agnostic 的——程式碼、文件、設定、schema 都適用。

**① 拿它重播你剛跑完的那一輪。**
對這一輪收下的每一條發現,指出它實際需要哪些證據,然後檢查在新管線下那些證據還到不到得了 reviewer。
**一個會漏掉現行管線剛剛產出的發現的改動,就是回歸,不管它省了多少。**
這是效能檢驗——它具體、可重播、無從爭辯。

> 2026-08-06 實測:「只審上一輪之後的 diff」被提出來,然後被它自己的重播殺掉。
> 那一輪最好的一條發現同時需要**被改的那一行**(`43 支`,在 diff 裡)
> **和**那條讓它成為錯誤的**沒被改的規則**(`投影母體是 42`,不在 diff 裡)。
> **缺陷住在新文字裡,讓它成為缺陷的判準住在舊文字裡。**
> 用「缺陷在哪裡」去界定 payload,是一個範疇錯誤。

**② 每一個量化宣稱,說出口之前先量。**
先跑 `wc`/`du`/計時器。同一場:「payload 從 140K 掉到 15K」被斷言了,從沒被量過;
誠實的差是 29,898 對 33,988 字元——**12%,不是 90%**。
提案裡一個沒量過的數字,是一個穿著白袍的猜測。

**③ 移除覆蓋要有機制化證明,不能拿分數當理由。**
只有在一個決定性檢查器現在涵蓋了某個 lane 的那條軸,**而且**那個檢查器通過了負向對照時,
你才可以退役或改用那個 lane。⛔ 「那個 lane 得零分」**不是**理由——
零分同樣可以解釋成*那個 lane 很弱*或*這只是一次安靜的抽樣*,拿它來砍就是
「縮小 payload」那個作弊向量穿了一件正當化的外衣。

**④ 說出你自己這個提案的失效模式。**
如果你講不出什麼會讓它是錯的,那你還沒想過它——把不確定性攤出來,不要攤結論。
還要分開「你的改動**造成**的」與「只是**同時發生**的」:一輪分不出
「我的改動有效」與「這份 artifact 剛好原生缺陷用完了」。說清楚哪些歸得了因、哪些歸不了。

**瞄準不是截斷。** 把 reviewer 對準被改的區域、同時仍然送整份 artifact,那是瞄準改動(過得了①)。
把其餘的刪掉,那是截斷改動(通常過不了①)。要知道自己在提哪一種。

#### 在花抽樣器之前,先把決定性檢查推到上游

reviewer 是**抽樣**;檢查器是**枚舉**。任何決定性工具判得了的東西,都不該送到 reviewer 手上:

- **程式碼**:送 diff **之前**先跑型別檢查、linter、測試。它們免費且窮盡;
  付錢給一個 LLM 去重新發現 `ruff`/`tsc`/`pytest` 已經標出來的東西,是浪費。
- ⛔ **「工具 X 回報乾淨」在工具的版本**和**規則集被釘死之前,都還不算一則主張。**
  否則它在輪與輪之間會安靜地改變意義,而你會把一次工具升級讀成自己碼的回歸。
  2026-08-07 實測:`uv tool run ruff` 解析到 latest,ruff 0.16.1 放寬了預設規則集,
  於是**在第 3 輪回報乾淨的同一份未改動的碼,在第 4 輪回報 21 個錯誤**——而第 3 輪的規則集仍然通過。
  釘死它,然後對每一條新浮出來的規則記下判定(採納 / 修了 / 駁回並附理由),
  免得下一個人重新推導一遍。同一個陷阱適用於任何會自動更新的檢查器:
  formatter、`npm audit`、型別檢查器、CI base image。
  - 這件事屬於這一輪的掃描,不只是它的前置設定:你的掃描涵蓋的是**你**寫的宣稱,
    而這是你的**工具**代替你寫下的宣稱。
- **其他 artifact**(文件、設定、schema):沒有現成檢查器的話,**那個缺口本身就是一條發現**。
  一支涵蓋你實際觀察到的那幾種宣稱形狀的 ~50 行腳本,勝過再跑一輪。
- 2026-08-06 一次文件審查實測:某一輪的 8 條發現裡,**5 條是決定性可計算的**
  (表格加總、被引用的 `file:line` 存不存在且是否真的那樣寫、
  一句「共用的、只有一處要改」的宣稱是不是真的只有一個位置、跨表判定一致性)。
  那一輪送了 **125K 字元**換到 **5 條 native 發現**——而一支腳本能在幾秒內**窮盡地**產出那一類發現,
  而不是一次一個抽樣實例。
  (注意這個勝利的形狀:不是「每條發現更便宜」,而是**拿到全部實例而不是一個**。
  那一輪 reviewer 指名了某個缺陷的 1 個位置,而它存在於 5 個位置。)
- 每一條收下的發現都應該留下一個**可重跑的斷言**——程式碼就是測試,文件就是檢查規則。
  之後「掃這條軸」的意思就變成*重跑那套檢查*,而不是*grep 一個字串*。

#### ⛔ 連兩輪命中**同一形狀**,是換方法的訊號,不是加一輪的訊號

上面那些停止條件讀的都是發現的**數量**——它們在 reviewer 乾掉的時候才會觸發。
還有第二種、更貴的失效是它們看不見的:**reviewer 還在產出,而每一輪都是同一個缺陷形狀的新實例。**
照數量規則那叫「繼續抽樣」,而你就會一直抽下去——每一輪都真的有斬獲,所以永遠不會有東西看起來不對。

**觸發條件:連續兩輪收下的發現都是同一個形狀的實例 ⇒ 下一輪改成「枚舉」輪,不是再抽一次樣。**
挑出那個形狀所在的那條軸,把它的成員逐一拿去打真正的程式路徑
(方法就是 Δ 關的方法,見 `/agent-sdlc:delta-enumerate`)。

> 2026-08-09 在一個 proxy 閘上實測:第 1–3 輪各自都命中了一條真發現,而三條都是同一個形狀——
> *守衛在比對位元組,而軸是段落身分*(該 PR 上這個形狀的第 3、4、5、6 次出現)。
> 數量規則說繼續。第 4 輪被我手動改成枚舉:**5 條倖存、5 條全收,其中兩條是第 1–3 輪剛做的修正裡面的洞**
> ——那正是抽樣無法再進入的區域。枚舉不是「再多一輪」,它是結束這個序列的那一輪。

- ⛔ **這是換方法,不是砍 lane。** 枚舉涵蓋的是抽樣器原本打的那條軸的超集合,
  所以它過得了上面的檢驗③——沒有任何東西被退役,枚舉輪如果沒把那條軸關掉,抽樣照樣接回來。
- ⚠️ **它自己的失效模式**:「同一形狀」是一個判斷,而兩條發現可以長得像卻不共用同一條軸。
  軸畫錯,你就會去枚舉錯的集合,同時抽樣器停止覆蓋其餘部分。
  緩解:枚舉之前先把那條軸明講出來;如果枚舉**之後**同一形狀又復發,那是軸畫錯了,不是樣本數不夠。

#### 輪數上限

- **預設上限:10 輪**,然後交給使用者做人審。
- ⚠️ **上限是預算,不是裁決。** 原本的理由(「超過 10 輪代表這是架構分歧,不是修得掉的發現」)
  **至少被實測推翻過一次**:2026-08-06 的一次文件審查,第 10 輪有全 run **最高**的採納率(7/8),
  而且產出了整份文件最大的一條修正——一個承重的數字錯了 **6 倍**,撐過了前面九輪。
  **它 8 條發現裡有 5 條是原生缺陷,不是 reviewer 在編修最近的編輯。**
- **所以用計分卡決定,不要用計數器**:只要 native accepted 還不是零,多跑幾輪就是正當的——
  把它說出來、把成本秀出來、讓使用者選。⛔ **每輪成本上升不是停下來的理由**(那就是上面那個提早停的陷阱);
  只有發現乾掉才是。停止條件是**連續兩輪 native accepted 為 0**(為什麼一輪不夠,見「讀 N 份結果」)。

## 多透鏡 fan-out(把單輪放大)

reviewer 是**非決定性的**:同一份輸入送兩次,發現幾乎不重疊。
所以一輪的沉默**不是**乾淨的證據,那只是一次抽樣。
串行跑 N 輪,花的是 N 倍 wall-clock,換到的覆蓋和一次抽 N 個樣本一樣。

**Fan-out 取代的是一輪「內部」的抽樣,它不取代輪迴圈本身。**
第 3(驗證)、4(修正)、5(收斂)步都不變——一個 fan-out 輪一樣以**不 commit** 收尾,
收斂條件一樣是「完整一輪回不出新的 `blocker`/`warn`」。

### 設計透鏡,不要複製 prompt

N 份同樣的 prompt 大多會重新找到同樣的東西。給每個 lens 一個**不同的問題**,並禁止它回答別人的問題。
在一份 24K 字元的稽核文件上有效的 lens:

| Lens | 只問 | 強制附上的證據 |
| --- | --- | --- |
| **數字** | 小計、分母、「N 項」這類宣稱加不加得起來 | 那段不成立的算術 |
| **矛盾** | 有沒有兩段話主張了不相容的事 | **兩段都引出來** |
| **違反自訂規則** | 這份文件有沒有違反它自己訂的規則 | **先引規則,再引違反處** |
| **結構 / 交叉引用** | 標題與內容符不符、「見第 X 節」解不解析得到 | 那個引用與它實際指向的目標 |

每個 lens 都加一段全域的「⛔ 超出範圍」區塊(它查不了的事實、沒拿到原始材料因此判不了的判斷)
——否則 lens 會漂移去對這個領域做臆測。

### 一次委派 N 個

機制歸 reviewer 實作管,不在這裡;v1 見 `sub-gemini` **模式 D**。
唯一一條不管什麼實作都會咬人的規則:**平行送出沒問題,收割必須序列化**,
因為背景分頁永遠不會渲染串流回應。它的失敗是**安靜的,而且看起來就像「還在想」**。

### 讀 N 份結果——數量不等於可信度

- ⛔ **跨 lens 的一致不是真值訊號。** 有幾個 lens 提出同一條發現,量的是*這件事有多容易想到*,
  不是*它有多可能為真*。實測:四個 lens 各自獨立主張了同一條**錯的**宣稱
  (四個都跳過了「這段碼怎麼處理上游那個值」的檢查);而那一輪最有價值的一條發現來自**單獨一個** lens。
  **不管幾個 lens 提出,每一條都要自己驗(第 3 步)。**
- ✅ **一致真正的用處:定位你自己文字裡的歧義。** 當兩個獨立的 lens(或兩輪)用**同樣的方式**
  誤讀了**同一段**文字,那段文字就是真的不清楚,即使它們的結論是錯的。
  **駁回那條主張,同時把措辭修掉**——否則第 N+1 輪會重新發現它。
- **把駁回連同理由記下來**(第 3 步)。被駁回的發現會跨輪重複出現;沒有書面理由,每次都要重新辯一遍。
- **依發現的性質停,不是依數量**——但要**連看兩輪**,絕不只看一輪。
  當 reviewer 不再找到你漏掉的東西、開始共同編輯你的草稿,那就是收斂了,即使數量沒有下降。
  指標是計分卡的 **native accepted** 那一欄(第 5 步)。
  - ⛔ **一輪是一次抽樣——它不足以當停止依據。** 2026-08-06 實測:第 8 輪產出 2 條發現,
    **兩條都是關於前一輪自己的編輯**——照單輪規則那就是「收斂了,停」。
    然後第 9、10 輪產出了**再 9 條被收下的發現,大多是原生缺陷**,包括該 run 最大的一條修正。
    停在第 8 輪就會把它 ship 出去。
  - 所以:**連續兩輪 native accepted 為 0** 才停。

### 分頁衛生

**收割完一個 reviewer 分頁就立刻關掉**——那是「拿到結果」的一部分,不是留待之後的清理。
之後可能想回看就把對話 URL 記下來;不要把分頁當書籤掛著。

## 與 pack 其他 skill 的關係

- 通常在 `/agent-sdlc:pr-prepare` 之後跑;修正收斂後更新 PR。
- **不是人審的替代品。** 被 `classify-change` 判成 **core** 的變更仍然需要逐行的人審——
  這支 skill 是那次人審的助手,不是它的替身。

## Context 檢查點

長 review loop 很吃 token。每輪結束檢查 context 用量;偏高先更新 mem-tmp 續接塊,再提醒使用者 `/compact`。

「幾分鐘前才剛被證明在這條軸上想得不夠寬」的人寫下的——而那正是另一輪**抽樣**在結構上看不見的位置,
因為它看起來已經修過了。最後一輪乾淨的意思是「reviewer 用抽樣沒找到新東西」,
永遠不是「那些修正夠寬了」。**不要讓這裡的一輪乾淨頂替掉 Δ。**
