# prompt-audit(中文鏡像)

> 📌 本檔是 `SKILL.md`(英文權威版)的中文鏡像,給中文語系維護者/讀者閱讀用。**Claude 實際載入/觸發的是英文 `SKILL.md`;本檔不會被當 skill 觸發。** 兩版內容一一對應,**每次改動兩版必須一起更新**。

多數 AI 寫程式的失敗,根源都在單薄的 prompt。一則花 30 秒寫、Claude 花 2 分鐘「執行」的 prompt,產出的程式碼往往要花 2 小時去修。這支 skill 在事情發生前就攔下來。

## 何時使用

只要使用者在評估、草擬、或即將送出一則做非瑣碎程式工作的 prompt,就用。觸發情境包括:

- 「這 prompt 好不好?」
- 「審一下 / 幫我看 / 檢查我的 prompt」
- 「Claude 看得懂這個嗎?」
- 「這 prompt 我要怎麼改進?」
- 使用者貼上一則 prompt 並問任何相關問題
- 你注意到使用者即將為一個複雜任務送出模糊的 prompt——主動提議幫他審

不要審:

- 使用者自己滿意的單行拋棄式 prompt
- 純聊天 / 澄清訊息(不是真正的任務 prompt)

## 六個必要要素

一則做非瑣碎工作的好 prompt,六個要素都要有。缺任何一個,成功率都會明顯下降。

| # | 要素 | 回答什麼 | 為何重要 |
|---|---|---|---|
| 1 | **目標(Goal)** | 我們在解決什麼問題?誰用這個結果? | 沒有目標,Claude 會優化錯的東西 |
| 2 | **範圍(Scope)** | 哪些檔案 / 模組可以改?哪些不行? | 沒有範圍,Claude 會動到不該動的 |
| 3 | **既有模式(Existing patterns)** | codebase 裡有什麼是我們該模仿的? | 沒有模式,Claude 會重造慣例、前後不一致 |
| 4 | **限制(Constraints)** | 效能、依賴、相容性 | 沒有限制,Claude 會做出使用者不接受的選擇 |
| 5 | **驗證(Verification)** | 什麼測試能證明這是對的? | 沒有驗證,「完成」就沒有定義 |
| 6 | **完成定義(Done definition)** | 什麼時候可以標記為完成? | 沒有完成定義,Claude 會過度建置或建置不足 |

## 工作流程

### Step 1 — 解析 prompt

讀使用者分享的 prompt,判斷 6 個要素哪些「有 / 部分有 / 缺」。要誠實——「我們應該遵循好的模式」不算真正的既有模式引用;真正的檔案路徑才算。

### Step 2 — 為每個要素評分

每個要素分類為:

- ✅ **清楚(Clear)** — 具體、可操作、無歧義
- ⚠️ **模糊(Vague)** — 有提到,但太抽象、派不上用場
- ❌ **缺失(Missing)** — 完全沒處理

### Step 3 — 帶原因診斷

每個缺口,向使用者解釋「**在手上這個具體任務裡**」為何重要——不是泛泛的 best-practice 說教。範例:

> 「你的範圍缺失了——而因為這則 prompt 提到 `auth/`,Claude 很可能會改到 30 幾個其他端點都依賴的共用 auth middleware。那是 core 程式碼的變更,需要人明確承擔。」

### Step 4 — 也要留意過度約束

相反的失敗模式:一則 prompt 規定了每個變數名、每一行 pseudocode、每個內部步驟。這會讓模型變差,而不是變好。看到就標出來:

> 「你的 prompt 過度約束了實作。模型在拿到『目標 + 限制 + 模式』後被信任去寫程式碼時表現最好。把 prompt 當成帶一個新人——講清楚『什麼重要』,而不是『該打哪些字』。」

### Step 5 — 產出改寫版

永遠給一個更好的版本,即使原版還不錯。用這個結構:

```
[目標]
<誰用這個、完成的定義是什麼>

[範圍]
- 可以改:<清單>
- 不可改:<清單>

[既有模式]
- 模仿 <具體檔案或模組>
- 慣例:<例如 service.ts + route.ts + *.test.ts>

[限制]
- <效能、依賴、相容性>

[驗證]
- 3 個 e2e 測試:<1 happy + 2 error,以使用者角度描述>
- 手動:<若適用>

[完成定義]
- <具體檢查清單>
```

如果使用者的任務沒大到需要全部六個,就把用不到的拿掉,不要用 placeholder 灌水。

### Step 6 — 並排呈現 before/after

審查結尾放一個直接對比,讓使用者看見增益。範例:

```
改寫前(6 字):「加一個使用者活動報表端點。」
改寫後(~250 字):<完整結構化 prompt>
為何改寫更好:範圍現在明確了、既有模式點名了、驗證定義了、完成可衡量了。
```

## 值得點名的紅旗

在原始 prompt 裡看到以下任何一項,就明白講出來:

- **動到 core 程式碼卻沒承認。**「就把這個加到 auth middleware……」
- **完全沒有驗證。**「它應該會動。」
- **模糊的代名詞。**「弄好一點。」「修一下這個。」(好什麼?這個是什麼?)
- **全篇沒有任何檔案路徑。** 沒有路徑很難落地。
- **一則 prompt 暗示了多個 PR。**「把 auth 流程、使用者儀表板、還有報表都做出來。」建議拆開。
- **使用者顯然不懂的領域。** 你很難去 PM 一個你不懂的領域。問:「你要怎麼判斷這是對的?」
- **要 AI 幫忙寫 spec。**「你看看我們應該做什麼。」那不是 Claude 的活——那是產品工作。

## 輸出格式

審查用這個結構:

```markdown
## 審查總結
<1-2 句:整體裁決>

## 要素檢查
| 要素 | 狀態 | 備註 |
|---|---|---|
| 目標 | ✅ / ⚠️ / ❌ | <觀察> |
| 範圍 | ✅ / ⚠️ / ❌ | <觀察> |
| 既有模式 | ✅ / ⚠️ / ❌ | <觀察> |
| 限制 | ✅ / ⚠️ / ❌ | <觀察> |
| 驗證 | ✅ / ⚠️ / ❌ | <觀察> |
| 完成定義 | ✅ / ⚠️ / ❌ | <觀察> |

## 紅旗
<條列,或「無」>

## 改寫版
<完整改寫>

## 為何改寫更好
<2-3 個具體增益>
```

## 停止條件

以下情況結束這支 skill:

- 使用者已拿到改寫後的 prompt
- 或使用者回推:「就這樣就好。」(不要一直重複糾纏。)
